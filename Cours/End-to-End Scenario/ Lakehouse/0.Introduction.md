## Tutoriel : Data Analytics de A à Z avec un Lakehouse

Dans ce tutoriel, vous allez prendre l'exemple d'une organisation de vente au détail et construire son lakehouse de A à Z. La même approche peut être utilisée pour implémenter un lakehouse dans toute organisation, quel que soit le secteur d’activité.

Vous endosserez le rôle d'un développeur au sein de la société fictive **Wide World Importers** dans le domaine du commerce de détail et accomplirez les étapes suivantes :

- **Créer un espace de travail Fabric.**
- **Créer un lakehouse.**
- **Ingérer des données, transformer des données et les charger dans le lakehouse.**  
   Vous pouvez également explorer OneLake, une copie de vos données en mode Lakehouse et en mode point de terminaison d’analytique SQL.
- **Connexion à votre lakehouse à l’aide du point de terminaison d’analytique SQL** et création d'un rapport Power BI à l’aide de DirectLake pour analyser les données de vente dans différentes dimensions.
- **Orchestration et planification de l’ingestion** et du flux de transformation des données avec un pipeline.

### Exemple de jeu de données : Wide World Importers

Wide World Importers (WWI) est un importateur et distributeur de produits de nouveauté de gros qui opère à partir de la baie de San Francisco. En tant que grossiste, les clients de la WWI sont principalement des entreprises qui revendent aux particuliers. La WWI vend aux clients de vente au détail dans les États-Unis y compris les magasins spécialisés, les supermarchés, les magasins informatiques, les magasins d’attraction touristique et certains individus. WWI vend également à d'autres grossistes via un réseau d'agents qui assurent la promotion des produits au nom de WWI.

### Flux de données et de transformation
Comme décrit précédemment, nous utilisons les exemples de données de Wide World Importers (WWI) pour générer ce lakehouse de bout en bout. Dans cette implémentation, les exemples de données sont stockés dans un compte de stockage d’Azure Data au format de fichier Parquet pour toutes les tables. Toutefois, dans des scénarios réels, les données proviennent généralement de différentes sources et dans différents formats.


![image](https://github.com/user-attachments/assets/decbad8d-3f21-42ae-9af2-1a7571f68c82)


- **Source de données** : Nous utiliserons la table de faits Sale, qui a un dossier parent avec des données historiques pendant 11 mois (avec un sous-dossier pour chaque mois) et un autre dossier contenant des données incrémentielles pendant trois mois (un sous-dossier par mois). Pendant l’ingestion initiale des données, les 11 mois de données sont ingérés dans la table lakehouse. Toutefois, lorsque les données incrémentielles arrivent, elles incluent des données mises à jour pour octobre et novembre, et de nouvelles données pour décembre. Les données d’octobre et de novembre sont fusionnées avec les données existantes et les nouvelles données de décembre sont écrites dans la table lakehouse, comme illustré dans l’image suivante :

![image](https://github.com/user-attachments/assets/22ba7211-49d5-4c91-b887-e1907550a5fa)


- **Transformation** : pour la préparation et la transformation des données, il existe deux approches différentes. Nous utiliserons les Notebooks/Spark pour les utilisateurs qui préfèrent une expérience code-first et les pipelines/flux de données pour les utilisateurs qui préfèrent une expérience low/no-code

- **Visualisation** : nous utiliserons le DirectLake de Power BI pour créer des rapports, des tableaux de bord et interroger directement des données à partir du lakehouse. Nous verrons aussi comment rendre nps données disponibles pour des outils de reporting tiers avec le point de terminaison SQL.
